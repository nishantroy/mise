# Mise: build notes

Decisions and deviations from `PLAN.md`, plus checks that need a real device.

## Decisions and deviations

- **Generated project is not committed.** `Mise.xcodeproj` is in `.gitignore`; run `xcodegen generate` after cloning or after editing `project.yml`.
- **Info.plists are hand-written** (`App/Info.plist`, `ShareExtension/Info.plist`) rather than generated by XcodeGen, so the `AppGroupID`, export-compliance and extension keys are visible in the repo.
- **RecipeKit uses `swift-tools-version: 6.2`** (needed for `.iOS(.v26)` in `platforms`), Swift 6 language mode. Tests use Swift Testing (`import Testing`).
- **A `MiseUITests` target was added** to `project.yml` (the amendments ask for XCUITests); it is wired into the `Mise` scheme's test action.
- Build output goes to `build/` (ignored), via `-derivedDataPath build/DerivedData`.

- **Fixtures (M1).** Serious Eats returned HTTP 402 to curl, and NYT Cooking is paywalled, so the five fixtures are: The Woks of Life (`@graph`, Shaoxing wine), Indian Healthy Recipes (Indian blog, `@graph` + `HowToSection`), BBC Good Food (top-level object, `ImageObject`), RecipeTin Eats (`HowToSection`), and Wikibooks Kung Pao Chicken (no JSON-LD). Each was trimmed to `<title>`, `og:` meta tags and the JSON-LD blocks (Wikibooks: the article body), with a comment giving the source URL.
- **Text fallback headings.** Besides "Instructions / Directions / Method / Steps" the fallback also accepts "Preparation", "Procedure" (Wikibooks) and "How to make". Sub-headings inside the ingredient list (`<h3>`, or pasted lines ending in ":") are skipped rather than parsed as ingredients. When the page has heading tags, steps stop at the next heading; for pasted text they stop at a "Notes / Tips / Nutrition…" line.
- **Text fallback title** is `og:title` or `<title>` with a trailing " - Site name" and a wiki namespace prefix ("Cookbook:") removed. The image comes from `og:image` when present. Lines that are only wiki section-edit links ("edit", "[edit]") are dropped; the phone gets Wikibooks' mobile skin, which puts one beside every heading (fixture `wikibooks-kung-pao-chicken-mobile`). Servings are detected from "Serves N / Servings N / Makes N" above the ingredients; time is not parsed in the fallback.
- **Ingredient names keep their original case** ("Shaoxing wine"), not lowercased as in the plan's example; matching lowercases internally.
- **Notes from the JSON-LD path:** none (`notes` stays empty); section names in `HowToSection` are dropped and their steps flattened.
- **Cuisine** with several values is joined ("Asian, Indian").
- **Quantity formatting:** cooking units use ⅛ ¼ ⅓ ½ ⅔ ¾ glyphs (values ≥ 10 round to whole numbers); g/kg/ml/l/oz/lb use decimals, rounding to the nearest 5 above 100.
- Extra units beyond the plan's list: dash, slice, stalk, sprig, bunch, handful, inch, piece, packet, fl oz.

- **Catalog size (M2).** `ingredients.json` had 204 entries and `swaps.json` 120 at M2 (212 and 123 after the review fixes) (the plan said ~150 / ~60); more coverage across the owner's cuisines made the swap tables more useful. Both are checked by a test that every swap id exists.
- **Catalog matching does not strip prep words before matching.** Whole-word, longest-alias containment already ignores extra words, and stripping "chopped"/"crushed" would break aliases like "chopped tomatoes" (canned) and "crushed red pepper". Prep words *are* stripped when building pantry keys for names the catalog doesn't know. Matching also folds diacritics and applies a light singular rule ("onions" → "onion") to both sides.
- **One review item per ingredient.** Priority: conflict > dislike > missing > have (fine) > specialty/rare ("Do you have X?"). The spicy check is not a separate card when another flag applies; instead every item carries `suggestedScale = 0.5` for spicy ingredients when `spiceLevel <= 1`, and an otherwise-fine spicy ingredient gets a `tooSpicy` card.
- **Swap ranking bonuses need at least one component**, so "Leave it out" never gets the +3 "all in pantry" bonus vacuously. For conflict, dislike, missing and ask cards, "Leave it out" is appended after the top 3 when the table has it.
- **Step rewriting** masks longer catalog aliases that contain the target ("dark soy sauce" while swapping "soy sauce"), replaces longer aliases first, and capitalises the new name only at the start of a sentence. Leave-it-out (remove) edits don't touch steps.
- **Swapped-in ingredient names are the catalog display name** (first alias, lowercase, e.g. "dry sherry").

- **Feedback clause splitting (M3).** Sentences split on `. ! ? ;` and newlines; clauses on commas and "but / so / then / because", and on "and" only when a new clause follows ("…breast and it was too salty"), so "skipped the cilantro and sesame oil" stays one list.
- **"Too salty" with several salty ingredients** produces one edit per ingredient (salt, soy sauce, dark soy, tamari, fish sauce). So the plan's mixed sentence gives exactly 3 edits on a recipe with one salty ingredient (tested on a simple recipe and on the RecipeTin chow mein fixture); on a recipe with both soy sauce and "salt to taste" it gives 4 (scale + "Use less salt than last time" note, per amendment 6). Taste rules with no matching ingredient fall back to a note.
- **Removals and scalings are all-or-nothing over a list**: every item must match a recipe ingredient, otherwise the clause becomes a note (covers amendment 11 for "no problem" etc.). Pure filler ("no changes", "nothing", "ok") is dropped rather than saved as a note.
- **"added X" where X is already in the recipe** (and X has no amount) becomes "more X" (×1.25).
- **Edit summaries** show amounts where known: "Less soy sauce: 2 tbsp → 1 ½ tbsp".

- **DESIGN.md was added mid-build** (owner request, arrived during M4). It is committed with M4, the first milestone that uses it. All colour tokens are colour sets in `App/Assets.xcassets/Mise/` (light + dark), exposed as `Color.mise.*`; spacing, radii, fonts and the shared components (`MiseCard`, `SectionCard`, `RecipeCard`, `Chip`/`ChipGroup`, `PrimaryButton`/`SecondaryButton` + button styles, `Badge`, `ReviewCard`, `EmptyState`, `PageDots`, `FlowLayout`) live in `App/Theme/`. `AccentColor` and `LaunchBackground` mirror the `accent` and `background` tokens.
- **Contrast (checked with a script against the hex values):** every text/fill pair in the spec passes 4.5:1 except `accent` text on `surfaceSunken` in light mode (4.37:1), which the spec prescribes for secondary buttons; their label is 17pt semibold, which qualifies as large text (3:1). Badges use a 12% tint fill instead of the spec's 15% so `herb` text on it reaches 4.65:1 (15% gives 4.46:1).
- **Preference controls are chips everywhere** (diet, avoid, spice level, cuisines, weeknight time), in onboarding and Settings, instead of a Picker/Slider, so both screens share one set of editors. Household size is a system Stepper.
- **Onboarding keeps the plan's 4 pages** (diet + avoid; dislikes + heat; cuisines + time + household; pantry), so a page can hold two or three short questions rather than strictly one.
- **Pantry "cards"** are inset-grouped List sections with `surface` rows on the cream background, which keeps native swipe actions; Have/Missing headers are serif.

- **Clipboard (M5).** The link field is not prefilled from the clipboard on appear (amendment 2): reading `UIPasteboard.general.url` triggers the paste prompt. A `PasteButton` fills the field in one tap instead. Share-extension URLs (M8) do prefill it.
- **Stubbed network in UI tests.** `-uiTesting` uses a separate store file (`MiseUITest.store`), `-resetData` deletes it first, and `MISE_STUB_PAGES` (JSON of URL → HTML, built by the UI test from the RecipeKit fixtures that are copied into the UI-test bundle) swaps in `StubRecipeFetcher`. `RecipeFetching` and the fetcher are injected through the SwiftUI environment.
- **Revision 1 on import** is always recorded: "Imported" or "Imported: Swapped Shaoxing wine for dry sherry; …". `originalData` is the recipe as parsed, before swaps, so "Reset to original" also undoes import-time swaps.
- **Spicy-only cards** default to "Use half" switched on; other cards offer it as an off-by-default toggle when the user likes mild food. A chosen swap wins over halving.
- **"Do you have X?" → Yes** writes `have` and collapses the card; **No** writes `missing` and reveals the swaps in place. The review list is computed once when the screen opens, so answering doesn't reshuffle the cards.
- **Recipe detail landed in M5** (needed to verify the saved swap); M6 adds the adjust flow.

- **Adjust flow (M6).** Selected quick chips (except "Perfect") and the free text are joined into one feedback string for the assistant. "Perfect" isn't parsed; it sets the rating to thumbs-up if no thumb was chosen. Feedback that was typed but never run through "Suggest changes" (or changed since) is saved as a note, so nothing is lost. Every save bumps `timesCooked` and records a revision ("Cooked it" or "Cooked it: …"), even with no edits. If the assistant throws, the view falls back to the rules.

- **Foundation Models (M7)** follows the installed iOS 26.5 SDK: `SystemLanguageModel.default.availability` (`.available` / `.unavailable(.deviceNotEligible | .appleIntelligenceNotEnabled | .modelNotReady)`), `LanguageModelSession(instructions:)`, `respond(to:generating:options:)` with `@Generable` `EditPlan`/`GeneratedEdit` (kind is a `@Generable` enum; non-optional fields with ""/1.0 defaults; `factor` guided to 0.25…3.0, at most 6 edits) and `SwapPlan`. Temperature 0.2 for edits, 0.3 for swaps. Prompts send ingredients (≤30) and steps (≤10, truncated), never page HTML.
- **Mapping model output lives in RecipeKit** (`ProposedEdit`), so it is unit-tested with `swift test`: names map back through the same matcher as the rules; unknown ingredients, no-op or absurd factors and empty notes are dropped; one edit per ingredient; "add X" where X is already in the recipe becomes "more X"; a split "1 tbsp" + "lime" is recombined (seen in the simulator).
- **If the model returns nothing usable**, the rules' edits are used. Any thrown error (guardrail, context window, decoding…) is logged with `os.Logger` and falls back to the rules silently. Prompts and outputs are logged in DEBUG builds (subsystem "Mise", category "FoundationModels").
- **The simulator here exposes the model** (it reports `.available`, via the host Mac), so `AssistantUITests.testModelPathWhenAvailable` runs the real model end to end; it skips itself where the model is unavailable. For "it was a bit flat, so I finished it with lime and more oyster sauce" on the chow mein fixture it proposed "More oyster sauce: 1 ½ tbsp → 1 ¾ tbsp" and "Add 1 tbsp lime". (The rules also catch this sentence via "finished it with"; they miss phrasing like "a bit flat" on its own.) All other UI tests launch with `-forceRules`, which is how the rules-only path is tested (amendment 12).
- **Availability is re-read when the app becomes active**, so turning Apple Intelligence on or off is picked up without relaunching. `-resetData` also clears the force-rules default.

- **Share extension (M8).** `PendingImports.swift` is compiled into both targets and reads the group ID from each bundle's `AppGroupID` Info.plist key. The extension accepts the first `public.url` attachment, falling back to a link found in shared plain text, and shows "Saved. Open Mise to finish importing." for about a second before completing (a plain UIKit card: the extension has no asset catalog, so it uses system colours rather than the theme). The app reads the queue each time it becomes active (only once onboarding is done) and shows one import sheet per URL in turn. *Changed in code review:* a URL is removed from the App Group list only when its sheet closes (saved or cancelled), so it survives the app being killed mid-import; URLs already queued or showing aren't added twice; `-resetData` also clears the queue. `-enqueueImport <url>` simulates the extension for UI tests.
- **The real share flow was driven in the simulator**: `SafariShareUITests` opens https://example.com in Safari, uses More → Share → Mise, returns to the app and checks the import sheet holds that URL. It passed here. It needs network access and skips itself when Safari's UI doesn't match (Share lives under the "More" menu in iOS 26 Safari).
- **UI-test helper hardening:** `completeOnboarding` taps Continue until the last page appears, because taps during the page animation were occasionally dropped.

- **Rule conflicts (found in M9 review).** When feedback both replaces or removes an ingredient and implies scaling it ("too salty" + "used light soy sauce instead of dark"), only the replace/remove is kept, and at most one scale per ingredient survives (`FeedbackParser.resolvingConflicts`).
- **M9 polish.** The placeholder icon is generated (1024×1024, no alpha): terracotta `#C2410C` with a cream New York serif "M" and a short rule beneath it. The launch screen is the `background` colour (`UILaunchScreen` → `LaunchBackground`). Empty states cover no recipes, no search matches, an empty pantry, no history and no suggested edits. VoiceOver: chips, radio-style swap rows and thumbs expose labels, values and selected traits; the review-card header, recipe cards, ingredient rows and step rows read as single elements; page dots read "Page n of 4". Every view has light and dark previews, and a few have an accessibility-5 preview.
- **Dynamic Type was checked in the simulator** at accessibility-XXXL with `ScreenshotTour` (with dark mode and the default size). All screens scroll and stay usable; at accessibility sizes the onboarding buttons stack vertically, the pantry grid drops to one column, and chips wrap their text.
- **Builds:** Release for the simulator succeeds, and an unsigned Release build for `generic/platform=iOS` (`CODE_SIGNING_ALLOWED=NO`) succeeds. *Correction (code review):* at M9 I wrote that the app was iPhone-only and that the "All interface orientations must be supported" warning was harmless. That was wrong. The project-level `TARGETED_DEVICE_FAMILY: "1"` was overridden by XcodeGen's target presets, so Mise and MiseShare built for iPhone and iPad ("1,2"). `TARGETED_DEVICE_FAMILY: "1"` is now set on each target. The generated project has no "1,2", the built Info.plists have `UIDeviceFamily = [1]`, and the orientation warning is gone from the device build.
- **Full UI suite (M9 run):** 11 tests, 10 passed, 1 skipped (`ScreenshotTour`, which is opt-in). In that run `testModelPathWhenAvailable` took about 24 minutes: the app sat in "Wait for com.nishantroy.mise to idle" for about 1,340 s right after launch, before any model call. Run on its own it takes about 60 s. The cause isn't known (possibly simulator load or the model warming up on the host); worth watching if it recurs.
- **TestFlight was not attempted** (out of scope per the amendments). README documents the team, bundle ID and App Group setup, running on a phone, and the TestFlight steps.

### Code-review fixes (after M9)

- **Step rewriting is a single pass** (one alternation regex, longest first, word boundaries). A new name containing an old alias ("olive oil" for "oil") is never rewritten again. Protected names come from the raw catalog names plus simple plural/singular forms, so "spring onions" survives an onion → shallot swap.
- **Ingredient lookup in feedback.** Same catalog ID first. *Judgement call:* if the catalog knows the text but that entry isn't in the recipe, the review asked for "return nil". I return nil except when a recipe ingredient's name contains every word of the text, so "skipped the chicken" still finds "chicken thighs" while "fish sauce" can never mean "soy sauce". Without a catalog match, overlap ignores generic head words (sauce, oil, powder, paste, seeds, leaves, juice, stock, flour, milk…).
- **Removal objects must be ingredients:** "time to…", "to rest…", "X cooker/pan/pot/oven…" are rejected, and the clause is kept as a note.
- **Taste rules:** a negation within three words before the phrase (not / never / no / hardly / …n't) means no edit. If the clause is only that, no note either, and praise-only clauses ("perfect", "just right", "so good") are dropped as filler. "Too hot" doesn't count as spicy when the clause mentions a pan, oil, oven, grill, heat, wok, etc. Text after "and / but / while" in a matched taste clause is kept as a note ("…and the garlic burned").
- **"added X …"** becomes "more X" only when the rest is just the ingredient's name. Timing or manner phrases ("at the end", "too early") keep the clause as a note, also for ingredients not in the recipe.
- **Splitting:** "." between digits isn't a sentence break, and "so" splits only before a new clause ("…so I used a pot", not "it was so good").
- **"1-1/2"** is a mixed number: a hyphen "range" whose upper value is below the lower is read as lower + upper when the upper is a fraction.
- **Free-from qualifiers** in the ingredient's own name cancel tags: gluten-free, dairy-free/non-dairy, egg-free/eggless, nut-free, alcohol-free/non-alcoholic, vegan/plant-based (all animal tags), vegetarian, meatless. Notes aren't checked, because "or gluten-free flour" in a note says nothing about the listed ingredient. New catalog entries (now 212): soy, oat, almond and other plant milks; rice flour; cornmeal/masa/polenta; coconut flour; gluten-free flour. Milk and flour got dairy-free / gluten-free swap options. *Judgement call:* "corn flour" stays an alias of cornstarch (UK usage) rather than cornmeal.
- **Pantry tab** uses `IngredientCatalog.exactMatch`: a typed item maps to a catalog ID only when every word of it is covered by the matched alias. "almond butter" stays "almond butter" instead of becoming "butter".

- **Ingredient check, repeated ingredients:** "Do you have X?" answers are keyed by pantry key, so an ingredient listed twice (marinade and sauce) is asked once and both cards update. Cards stay separate, because each line can take a different swap. Accessibility identifiers are `review.<key>`, then `review.<key>-2`, `-3`…
- **Rating:** tapping a thumb marks the rating as touched; deselecting it saves no rating (nil). If no thumb was touched, the "Perfect" chip still sets thumbs-up, and otherwise the old rating is kept.
- **Swap rows** hide the note when it repeats the title ("Leave it out").
- **Share timing (seen in the post-review suite run):** the app reads the App Group queue only when it becomes active. If you switch back to Mise within a second or two of tapping Mise in the share sheet, before the extension has written the URL, the link is picked up on the next activation instead. `SafariShareUITests` now waits 6 s before switching back. A Darwin notification from the extension would close this gap; not done.
- **Post-review test runs:** `swift test` 107 passed. Full UI suite (ScreenshotTour skipped): the first run had 2 failures, a 5 s wait for the adjust sheet in `testResetToOriginalIsRecordedInHistory` (raised to 10 s) and the share-timing race above. After those test-only timing changes both pass alone, and a full rerun passed 14/14.

### Cuisine guess and realistic time (post-v1 feature)

- **Catalog signals.** Entries that say something about the cuisine carry `"cuisines": [...]` and an optional `"cuisineWeight"` in `ingredients.json` (80 entries). The vote defaults to 3 for a single-cuisine entry (oyster sauce, garam masala, gochujang, mirin, tahini, chipotle…) and 1 for shared ones (soy sauce and sesame oil → Chinese/Japanese/Korean; coconut milk → Thai/Indian). Weak single-cuisine hints (turmeric, egg noodles, black beans, balsamic) are pinned to 1, mid ones (pasta, tortillas, harissa, lemongrass) to 2. Garlic, ginger, onion, scallion and the like have none. The vocabulary is `UserPreferences.cuisineChoices` (onboarding's list); a test checks every catalog cuisine and title keyword is in it. Fish sauce is Thai only, since Vietnamese isn't in the vocabulary.
- **New catalog entries:** `pancetta` (pancetta, guanciale; was an alias of bacon), `masa-harina` (was an alias of cornmeal) and `tomatillo`, so they can signal Italian/Mexican. Pancetta and masa harina are now "specialty", so the ingredient check asks about them; swaps added (pancetta → bacon, masa harina → cornmeal, tomatillo → tomato + lime juice).
- **Scoring** (`CuisineGuesser`): each catalog entry votes once per recipe; title keywords add 6 for a cuisine name ("Thai", "Sichuan", "Lebanese"), 4 for a dish ("kung pao", "carbonara", "bulgogi", "tacos"), 2 for a loose hint ("curry", "fried rice", "pasta"), one title vote per cuisine. A winner needs ≥ 3 points and a 2-point lead, else nil: soy sauce alone scores 1, and soy + sesame oil + rice vinegar is a three-way tie. "Strong" is ≥ 6 points and at least double the runner-up.
- **Model threshold.** `FoundationModelsAssistant.guessCuisine` asks the model (a `@Generable` enum of the ten cuisines plus `other`, temperature 0) only when the rules aren't strong. If the model answers, its answer wins, including "Other" → no guess (it reads the whole title and ingredient list, which beats weak rule evidence). On error/timeout the rules' answer (possibly nil) is used.
- **Storage.** `Recipe` gains `cuisineIsGuess: Bool` and `timeEstimate: TimeEstimate?`. `Recipe` now has a hand-written `init(from:)` using `decodeIfPresent` (missing → false / nil; the list fields also default to empty, and a malformed estimate decodes as nil rather than failing the recipe). Tested with v1-shaped JSON.
- **A page cuisine is never overwritten** (`Recipe.withInsights`); nor is one the user picked. A re-guess replaces an earlier guess, but a nil re-guess keeps it.
- **Changing a guess is a plain edit recorded as a revision** with no `RecipeEdit`s ("Cuisine set to Korean", "Cleared the cuisine (Chinese)"), like "Reset to original". No new `RecipeEdit` case, so revision JSON is unchanged. Picking the guessed cuisine itself confirms it (it stops being a guess). *Limit:* "Re-check time and cuisine" will guess again after the user cleared a guess; it's an explicit action, so that seemed acceptable.
- **Display.** Card metadata (via `RecipeFormat.metadata`, so `RecipeCard`/`RecipeListView` are untouched) reads "15 min · Chinese", "~1 hr 5 min · Chinese (guess)". On the detail, the guessed cuisine is a menu (name + a small sunken "guess" capsule) to pick another cuisine or clear it.

- **Time estimate rules** (`TimeEstimator`, all constants public and documented in code):
  - Durations per clause: "4 minutes", "2–3 minutes" / "30-40 mins" / "7 to 8 mins" (upper), "½ hour", "half an hour", "1 1/2 minutes", "1.5 hours", "1 hr 30 min", "1 hour and 15 minutes", "an hour and a half", "a minute", "one more minute", "a few seconds", "10-minute". "1 min on each side" counts twice. "Overnight" = 8 h passive and sets `isOvernight` (and wins over "4 hours or overnight"). Units are hours, minutes and seconds only; days/months aren't read.
  - Sentences that look like storage advice ("freeze for up to two months", leftovers, airtight, reheat) are skipped.
  - Passive when the clause says marinate, rise/proof, soak, chill/refrigerate, freeze, rest (not "the rest of"), cool (not "cool water"), set, set aside/stand/sit (not "stand mixer"). Everything else is active, including simmering and baking (you're cooking, even if hands-off).
  - Clauses split on sentences, ";" and "then". A step starting "Meanwhile"/"While"/"In the meantime", or a clause with "while the/it/you…", is treated as overlapping and not added.
  - Untimed work gets small defaults: an "until golden/soft/…" cooking sentence in a step with no time at all gets 3 min; "bring to a boil/simmer" or "comes to a boil" with no time in its sentence gets 5 min.
  - Prep: 1 min per ingredient line (water, salt and black pepper excluded), min 5, max 25.
  - Total = prep + active + passive, rounded to the nearest 5 (min 5). Active/passive are rounded up separately, so they can differ from the total by a minute or two.
  - **Mismatch** = estimate ≥ 1.5 × stated **and** ≥ 15 min longer (the suggested rule; it flags chow mein's "15 min" exactly at the boundary, 30 vs 15).
- **Model gaps.** `FoundationModelsAssistant.estimateTime` sends the title, ingredient names (≤ 30), steps (≤ 12, 140 chars each) and the rules' duration hints ("step 2: 30 min marinating, waiting", "untimed steps: 4"). It asks a `@Generable TimeGaps { prepMinutes 0–90, untimedMinutes 0–180, reason }`. The model's prep replaces the per-ingredient allowance and its untimed minutes replace the rule defaults; timed durations always come from the rules. RecipeKit clamps (*superseded:* now bounded relative to the rules' own values, see "Stale and inflated time estimates"; negative → ignore the proposal, reason cut to one line ≤ 160 chars, empty reason → a default) and marks `source = .model`. Any error falls back to the rules.
- **Import waits for the insights.** They run after parsing, before the ingredient check, in parallel (`RecipeInsights.enrich`, `async let`), behind the existing Import spinner. Model calls have a 12 s timeout each (then rules). The result is stored on the recipe (and so on `originalData`).
- *(Superseded by "Stale and inflated time estimates": edits now get the rules' estimate at once, refined by the model in the background.)* **Recompute only at import and on "Re-check time and cuisine"** (detail menu), not after edits. Edits rarely change timing, and a cheap rules recompute after an edit would silently replace a model-backed estimate. Re-check writes onto both the current and original versions (so "Reset to original" keeps it), isn't a revision, and doesn't bump `updatedAt` (the list order is unchanged).
- **Detail display.** The metadata row keeps the stated time ("15 min"), or "~1 hr 5 min" when the page had none. A second line appears only when it adds something: "Realistically ~30 min (11 min marinating) · recipe says 15 min" on a mismatch, or "Estimated ~1 hr 5 min (30 min marinating)" with no stated time; overnight reads "overnight + ~40 min (marinating)". Tapping the line shows the reason. When the estimate is *lower* than the stated time nothing extra is shown: the rules don't know about unstated work, so a lower number is more likely missing time than a faster recipe. "Longer than your weeknight time" appears when the larger of stated and estimated time exceeds `weeknightMinutes`.
- **Fixture results (rules):** Kung Pao (Wikibooks, both skins): Chinese (score 17 vs 3), no stated time, estimate 65 min (22 prep, ~12 cooking incl. 3 for heating the wok, 30 marinating). Chow mein: Chinese (page also says Chinese), stated 15, estimate 30 → mismatch. Indian curry: Indian (14 vs 1), stated 50, estimate 40. Pancakes: nil (page says British), stated 30, estimate 40 (30 min optional rest counted). Pork belly: Chinese (12 vs 1), stated 105, estimate 80.
- **Test runs for this feature** (on the "iPhone 17" simulator, `-derivedDataPath build/DerivedData`): `swift test` 144 passed (37 new). Full UI suite 16 passed, 1 skipped (`ScreenshotTour`), including the two new `InsightsUITests`. The first run of the new tests, on a freshly booted simulator, failed in the shared helpers before reaching new code (the Recipes tab took more than 10 s to appear after onboarding, and a URL-field tap didn't take keyboard focus). After booting the simulator first, both passed on their own and in the full suite.
- **Weak spots.** No batch multiplication ("cook the pancakes in batches"); optional waits ("rest 30 mins if you have time") are counted; untimed steps get flat defaults, which undercount long "cook until thick" steps (the model is meant to fill these); prep is per line, so a recipe with many spoonfuls of sauce (Kung Pao, 22 lines) gets a generous allowance, and prep done during a marinade isn't overlapped. Cuisine: recipes outside the ten cuisines (Vietnamese, Greek, British…) are either nil or pulled toward the nearest signal (fish sauce → Thai) when the model isn't there to say "Other".

### Paste my version (post-v1 feature)

- **Fixtures.** `mongolian-beef-my-version.txt` is the owner's write-up, verbatim. `woksoflife-shortcut-mongolian-ground-beef.html` was downloaded with a Safari user agent and trimmed like the others (title, `og:` tags, the JSON-LD graph, a source comment). Note the page's `og:title` is "Make Mongolian Beef FAST with This Shortcut!"; the JSON-LD name "Shortcut Mongolian Ground Beef" wins.
- **Step-style parsing** (`StepStyleParser`, used by `RecipeImporter.parse(text:)` only when the classic "Ingredients" parse fails). First line = title, servings from "(serves 4)", "– serves 4", "[makes 12]" or a "Serves 4" line. Every other line is a step, kept verbatim (only bullets / "1." numbering and chat-app markdown `**`/`#` are removed). *Decision:* section labels are **dropped**, not prefixed: a label is ≤ 4 words and ≤ 32 characters, no digits, no sentence punctuation, and followed by a line that isn't a label; a line ending in ":" always is. The last line is never a label, so a closing "Serve hot" survives. Needs ≥ 2 ingredient mentions, so random prose isn't a recipe.
- **Mention rules** (`StepIngredientExtractor`): split each step at top-level `, ; :` and sentence ends and at "and / with / plus / then" (parentheses kept with their item); in each piece, a mention starts at the first number, fraction glyph or "a/an/one + unit" ("a handful of") and stops at a preposition (in, into, over, on, to, for, until, at, from…); after the stop the rest is scanned again ("4 cloves garlic in 2 tbsp butter" gives both). Each mention goes through `IngredientLineParser` and the catalog. Rejected: numbers after "for / into / every / after / at / by / to / than / until…", anything with "°", and names that are durations or counts ("min", "sec", "pieces", "batches"…). "X or Y" → name X, note "or Y". Ranges keep the parser's rule (upper bound: "1–2 Fresnos" → 2).
- **Model path.** `RecipeAssistant.extractIngredients(steps:title:)` (default: the rules). `FoundationModelsAssistant` asks a `@Generable IngredientExtraction { lines: [String] }` (≤ 40, temperature 0, 12 s timeout) and never touches the steps. `ModelIngredientLines.map` validates in RecipeKit: drops lines over 80 chars or with more than one sentence, bare amounts, durations, repeats, and anything not grounded in the step text (every content word of the name, or any alias of its catalog entry, must appear). `choose` keeps the model's list only if it has ≥ ¾ of the rules' count (min 2); otherwise the rules. Any error → the rules.
- **Diff** (`RecipeDiff.compare(current:mine:pantry:)`), in order: (1) same catalog ID, picking the closest amount when the original lists it twice (soy sauce in marinade and sauce); (2) same normalised name; (3) an added entry with `replaces` in the catalog (`ginger-garlic-paste` → `["ginger","garlic"]`) takes all of those still unmatched: two or more → one new `replaceIngredients(ids:with:reason:)` edit, one → a plain replace; (4) swaps table, best quality first, single-component options only, then the table read backwards (sugar → brown sugar uses brown sugar's entry). Replacements carry the user's amount. Matched pairs: same unit and ≥ 15% different → scale; different units (¼ cup vs 1 tbsp) → a replace that keeps the ingredient and takes the user's amount, flagged by `RecipeEdit.amountChangeReason` so its summary reads "Change neutral oil: ¼ cup → 1 tbsp" and step text isn't rewritten (a scale would have shown "⅛ cup"). Then removes, adds, and `replaceSteps` when the steps differ. Existing notes aren't compared; new ones from the paste are offered (see "Pasted write-ups" below).
- **New edit cases** `replaceIngredients` and `replaceSteps` are appended to `RecipeEdit`; synthesised `Codable` keys each case by name, so existing revision JSON decodes unchanged (tested with hand-written v1 JSON and an exact-encoding check). An older build can't read revisions containing the new cases; acceptable for a TestFlight app that updates as a whole.
- **Summary wording fixes.** "Half the" / "Double the" now only for factors ≈ 0.5 / 2 (a ⅓ scale used to read "Half the"); a removal of one of two same-named lines says which ("Leave out soy sauce (1 tsp)").
- **Title and servings** are offered as extra toggles, not `RecipeEdit`s: "Rename to “…”" is **off** by default (keep the original title unless the user opts in), "Serves 4 (was 6)" is on. Amounts are compared as written, not normalised by servings (the user wrote what they cooked). Both go into the revision summary.
- **Pantry learning** (judgement call on scope): swapped-out specialty/rare ingredients → "don't have" unless the user's version still uses them (staples and common items are never marked missing this way: swapping fresh ginger and garlic for a paste doesn't mean they're out of garlic); ingredients in the user's version → "have" only when the catalog calls them specialty/rare or the pantry currently says missing, since the ingredient check assumes staples and common items anyway (offering "have" for water and salt would be noise). Updates the pantry already reflects are left out. Each is a toggle, ticked by default, labelled "Pantry: Shaoxing wine → don't have". For the Mongolian beef pair only Shaoxing wine is offered as "don't have".
- **Catalog:** `replaces` field on `CatalogEntry`; `ginger-garlic-paste` gains it plus aliases; new `fresno-chili` (common, spicy); `dried-chili` gains "dried red chili peppers". "sherry" was already an alias of dry sherry and "lao gan ma" of chili oil.
- **The model doesn't refine the diff.** The brief allowed it via the hint pattern; the rules give the expected result on the fixture, and pairing mistakes from a small model seemed riskier than useful. Not done.
- **UI.** Entry points: the detail menu ("Paste my version", its own sheet) and a small "Paste your own version instead" link at the bottom of "I made this" (pushes the same screen; saving there also counts as a cook). The screen: text box + `PasteButton` + Compare, then one "Changes" card with the edit toggles, servings/title toggles and, under a divider, the pantry toggles (shared `ProposalToggle`/`EditProposal`, also used by the adjust screen), then Save. Editing the text after comparing disables Save until you compare again. Save calls `SavedRecipe.applyVersion`: ticked edits + opted-in title/servings, one revision "Your version: …", `originalData` untouched.
- **Share extension text.** The activation rule adds `NSExtensionActivationSupportsText` (web URLs still allowed). Recipe-like text (≥ 3 lines, or ≥ 120 chars that aren't a link) wins over a URL, so a claude.ai write-up shared with a chat link stays text; otherwise the URL, then a link in short text, then any text. The App Group list keeps its key; URLs are still stored as plain strings and text items as `{"type":"text","id","text"}` dictionaries, read with `array(forKey:)`, so URLs queued by an older extension still drain. Text is capped at 20,000 characters. The app shows a "Shared text" sheet: "Save as a new recipe" (Import's Text tab, prefilled) or "use it as your version of…" a saved recipe, ranked by title word overlap (`TitleMatcher`, best first with a "Best match" badge), which opens "Paste my version" already compared. `-enqueueTextBase64 <base64>` simulates the extension for UI tests (base64 because a multi-line launch argument arrived as just its first line, so the first share-text test runs failed with "Couldn't read a recipe").
- **Weak spots.** Ranges lose their lower bound in display ("2 Fresnos" for "1–2"). Ingredients mentioned only without an amount ("serve over rice", "the rest of the green onions") aren't extracted; that's deliberate but means a step-style recipe never lists garnish-only items. A multi-replace rewrites both old names in the original steps, so "the ginger and garlic" becomes "the ginger garlic paste and ginger garlic paste" if the user keeps the old steps (*fixed in cook mode work, below*). Amount matching picks the closest amount, which can pair the wrong one of two same-ingredient lines when the user changed both. Word numbers ("two eggs") aren't amounts. Real share-sheet behaviour of the claude.ai app (what attachments it sends) is unverified.

### Pasted write-ups: prose, notes and model assembly

The owner pasted a markdown write-up from claude.ai (fixture `mongolian-beef-my-version-markdown.txt`, verbatim) and its closing commentary became step 12. *The step-style bullet above ("every other line is a step") and the "Model path" bullet (ingredients only) are superseded by this section.*

- **Markdown.** Whole-line `**bold**` / `__bold__` and `#` headings (≤ 6 words, ≤ 40 chars, no closing punctuation) are section labels, as well as the old plain-label rule. `- `, `* `, `•`, `1.`/`1)` mark list items.
- **Prose (`PasteProse`).** A line isn't a step when: it's under a "Notes / Tips / Variations / Make ahead / Storage" heading; it starts "Tip: / Note: / Variation: / Optional:"; it's unbulleted and after the last list item of a list-style write-up and doesn't start with a cooking verb ("Serve hot" still is a step); or every sentence in it is a tip or commentary. List items are always steps (so "Add chili if you want heat" in a bullet stays a step). Mixed lines ("Simmer 5 min. If it's thick, add water.") are never split.
- **Tip vs commentary.** Tips: "If …" (not "If using"), "For more/extra/a …", "go/use/add up to", "if you want/like/prefer…", "you can", "feel free". Commentary: "… are the fixes / is the key / the secret …", "fix for", "This works / This version / These tweaks …", "why this works", "compared to / than before / last time", chat openers and sign-offs ("Here's", "Enjoy", "Hope this helps", "Let me know"). *Decision:* tips → recipe **notes**; commentary → **dropped** (it explains a past conversation, not the recipe; kept in `Analysis.dropped` for validation). Other sentences in a prose line are kept as a note, so only recognised commentary is ever lost. "Go up to X if you want Y" is tidied to "For Y, use X." Ingredients still come from steps only, so the tip's "½–1 tsp" never becomes an ingredient.
- **Diff.** Notes the recipe doesn't already have (case/whitespace-insensitive) become `.addNote` edits after the steps, ticked by default like other proposals ("Note: For a clear tingle, use ½–1 tsp Sichuan peppercorn."). Applying appends to the notes card. New recipes pasted via Import get the notes directly.
- **Model assembly.** `RecipeAssistant.assembleRecipe(text:rules:)` (default: the rules' recipe) replaces the ingredient-only call in `PastedRecipes` for step-style pastes. `FoundationModelsAssistant` sends the paste (≤ 4,000 chars) and asks for `@Generable AssembledRecipe { servings 0–24, ingredients ≤ 40, steps ≤ 20, notes ≤ 4 }`, temperature 0, 25 s timeout (a whole recipe is a longer answer than the 12 s calls). `RecipeAssembly.merge` validates **per part**, keeping the rules' version of any part that fails (*decision:* a bad note shouldn't throw away good steps): steps (all or nothing) must keep every number and temperature of the source steps and add none, each step's content words must be ≥ 70% from the source steps and < 25% prose-only words (so commentary or a tip can't become a step), and ≥ 60% of every source step's words must still appear; ingredients go through `ModelIngredientLines.map`, then any amount must appear, with its unit, in the same list item of a source step that names the ingredient ("3 tbsp soy sauce" is rejected even though "3 tbsp sugar" and "soy sauce" share a step), amount-less lines ("rice") are allowed unless they repeat one with an amount, and `choose` still needs ≥ ¾ of the rules' count; notes must not be commentary, use only numbers in the paste, have ≥ ¾ of their words in the paste and at least one prose-only word (so a step can't be repeated as a note), and are used only if there are at least as many as the rules found. Title is always the rules'; servings the rules', else the model's if the paste says "serves N". Any error/timeout → the rules' recipe. `extractIngredients` stays in the protocol but the app no longer calls it, so a failed assembly no longer gets a second, ingredient-only model try.
- **Tests.** `swift test`: 206 passed (13 new: 5 in `PasteProseTests`, 8 in `RecipeAssemblyTests`; no existing expectation changed). App scheme built for the simulator (`xcodebuild build`, generic iOS Simulator). Following the no-simulator rule, no simulator or UI tests were run, so the model path has **not** been run against the real model; its tests feed hand-written model output.
- **Weak spots.** The prose rules are English phrase lists; unusual commentary ("Way better than v1") becomes a note rather than being dropped, and a bullet that's really a tip stays a step. A bullet-less, one-line-per-step paste where a step reads like a tip ("Add chili flakes if you want heat") becomes a note. The model's steps are all-or-nothing, so one paraphrased number ("half an onion") sends every step back to the rules.

### Pasted write-ups with an ingredient list (second Paste-my-version fix)

The owner pasted a Pepper Chicken version (fixture `pepper-chicken-my-version.txt`, verbatim) and got 24 steps: the ingredient list, then the method. *Root cause:* the classic parser's heading regex didn't accept "**Ingredients (3–4 servings)**", so the paste fell through to step-style parsing, which assumed ingredients only ever appear inside steps; "Salt to taste" (a short digit-free bullet) was dropped as a section label, and the opening commentary became the title. The 15% amount threshold then hid most changes (2 → 1¾ tbsp is 12.5%). *Supersedes* "Every other line is a step" and the 15% threshold above.

- **One classifier.** `StepStyleParser.analyse` now runs first for all pasted text (`RecipeImporter.parsePasted`; the classic parser and step extraction are fallbacks) and returns `ingredients` as well. Sections decide: an ingredients heading (`Ingredients…`, "What you'll need", with any "(3–4 servings)"), a method heading (Steps/Method/Instructions/Directions…), a notes heading. Group labels (`*Pepper masala:*` italics, "**For the chicken**", "## Sauce", a bare "Chicken" after a blank line) keep the section. Under an ingredients heading every line is an ingredient unless it reads like an instruction (verb, "Label: sentence", two sentences), which starts the method; under a method heading lines are steps. Bullets never decide, and a list item is never a label.
- **Without headings**, a line is an ingredient when `ingredientLineKind` says so (leading amount incl. "Scant 1 tsp"/"a handful"; "X to taste/to garnish/optional"; or exactly a catalog name) and no step has been seen yet, or its whole labelled block is ingredient lines. Never a line with a cooking verb first, a "Label:" prefix, two sentences, a duration or °.
- **Title:** the first line that isn't a section heading or prose; chat prose before it is sorted (new commentary patterns: "… of the original", "Small tweaks only"). **Servings range:** `servings` = lower bound (as for "(Serves 4–6)"), `servingsRange` is passed to `RecipeDiff.compare(…servingsRange:)`, which offers no change when the recipe's servings are inside it.
- **Step labels kept** ("Toast: Dry pan…"): they read well in cook mode and the label is the cook's.
- **Listed ingredients skip the model** (`ingredientsFromSteps == false`); `RecipeAssembly.merge` also keeps listed ingredients, and `validSteps` rejects any model step that is a bare ingredient line.
- **Diff:** same-unit amounts: any difference is offered (`scaleThreshold` 0.5%); across units < 3% is a conversion. Size words ("2 large" → "2 medium") and qualifiers ("scant", now kept as the first note by `IngredientLineParser`) are amount changes, carrying an alternative measure ("1 lb (450 g)"). Whole vs ground form (black pepper → black peppercorns) is a replace by the user's line (`RecipeEdit.versionLineReason`, "Change black pepper (2 tbsp) to 1 ¾ tbsp black peppercorns"). Adds show a short note. **Guard:** `replaceSteps` is never proposed when ≥ 2 (or ≥ ¼) steps look like ingredient lines (`StepStyleParser.stepsLookLikeIngredients`); `RecipeDiff.stepsWarning` explains and the old steps stay.
- **UI:** the "Use your steps (N steps)" toggle lists steps 1–3 and the last one; the warning shows in the Changes card.
- **Result** on all five fixtures (verbatim, "For the …" groups + numbered bold labels, group headers only, no bullets, plain text): 15 ingredients, the 10 labelled steps, no notes; against the saved recipe: chicken 0.5 kg → 1 lb (450 g), oil 3 → 2½ tbsp, onions 2 large → 2 medium (~270 g), ginger garlic paste / coriander powder 2 → 1¾ tbsp, turmeric → scant 1 tsp, garam masala 2 → 1¾ tsp, black pepper → 1¾ tbsp black peppercorns, add ½ tsp cumin seeds (for tempering, optional), your 10 steps; salt, lemon juice, cilantro, chillies, curry leaves unchanged.
- **Repair:** detail menu (⋯) → "Reset to original" → confirm. It restores the *imported* recipe (`originalData`), i.e. fennel seeds, since the import-time swap is a revision on top; re-pasting then also offers "Swapped fennel seeds for cumin seeds" (tested).
- **Weak spots.** In plain text a bare name ("Chicken") right after a blank line and before an amount line is read as a group label. Interleaved per-group ingredients and steps without headings only work when each group is labelled. The amount-change edit keeps the original's name, so "bone-in" from "1 lb bone-in chicken" isn't carried over.

### Cook mode (post-v1 feature)

- **Entry and presentation.** "Start cooking" (primary) sits beside "I made this" (now a tall secondary button) at the bottom of recipe detail; they stack when large text doesn't fit (`ViewThatFits`). Cook mode is a `fullScreenCover` given the detail's `displayed` recipe, so amounts follow the servings stepper. The screen stays awake (`isIdleTimerDisabled` saved on appear, restored on disappear). Type is `.title2` for the step and `.title3` for lists, all text styles, so Dynamic Type works.
- **Pages** are a custom pager (one page in a `ZStack` with a push transition, Back/Next buttons and a horizontal `DragGesture`), not a paged `TabView`: only the current page is in the view tree, which keeps the UI test unambiguous and the timer bar outside the pages. Page 0 is the prep list; then one step per page; the last page's primary button is "Done", which closes cook mode and opens "I made this" from the cover's `onDismiss`. Close (✕) and Done ask for confirmation only when a timer is running; leaving cancels all timers and their notifications.
- **Step ↔ ingredient linking** (`StepIngredientLinker`). Phrases: the ingredient's name split on "or" and "/" (prep words dropped) plus its catalog aliases; one alternation regex, longest first, whole words, accent/case-folded, optional plural on each word ("chilies", "berries"). Longer catalog names that contain a recipe phrase but aren't in the recipe ("spring onions") are matched and ignored. Single-word fallbacks: a recipe ingredient's last word or a one-word catalog alias, when exactly one recipe ingredient's name contains it ("chicken" → chicken breast or thigh fillets); a word that is another catalog entry's alias only counts for an ingredient of the same catalog category ("rice" never means rice vinegar); when several contain it, the one with ≥ 2× the amount in comparable units wins ("oil" → 1 ½ tbsp peanut oil, not ½ tsp sesame oil), else unresolved. Generic words (sauce, paste, powder, stock, water…) are never fallbacks, so "the sauce" stays unresolved. An ingredient listed twice: the step's written amount, then a distinctive word shared with the line's note ("slurry"), then order of use. Ingredients no step mentions are shown on step 1's "For this step" and land in "Get out".
- **Timers** (`CookTimers`) reuse `TimeEstimator.durations`/`clauses`/`isStorageAdvice`: ranges use the upper bound and keep the range label ("3–4 min" → 4 min), "30 seconds to a minute" is one timer ("30 sec–1 min"), "1 min on each side" is a 1 min timer (re-read from its own text, so the estimate's doubling doesn't apply), overnight and storage advice give none. `CookTimerStore` stores an end `Date` per timer and the countdown is computed from it (`TimelineView`), so backgrounding doesn't drift; a sleeping task plus a check on becoming active finish expired timers. On finish: success haptic, system sound 1005, and an in-app banner (auto-hides after 10 s). Each start also schedules a local notification (`UNTimeIntervalNotificationTrigger`); permission is requested the first time a timer starts (`notDetermined` only); if denied, scheduling fails quietly and the in-app alerts still work. No foreground notification delegate, so the system banner doesn't double up with the in-app one. Several timers run at once; a compact bar under the header lists them on every page (tap to jump to the step, ✕ to cancel/dismiss); tapping a running chip stops it.
- **Prep list rules** (`PrepPlanner`), claim order chop → start early → mix ahead → get out, so each ingredient appears once (tested on all 8 fixtures):
  - *Chop and prep:* a cutting participle in the ingredient's note ("thinly sliced" → "Thinly slice"; notes starting "or …" describe alternatives and are skipped), a step clause that starts with a prep verb ("Slice …", "Toast and grind …"), or a participle right before a mention ("add the chopped onion"). One item per verb phrase. Mixing verbs (beat, whisk) are not prep.
  - *Start early:* "softened"/"room temperature" notes ("Bring 115 g butter to room temperature"); preheating the oven, bringing things to room temperature, and boiling water anywhere in the recipe; marinating/soaking/rising/chilling (≥ 5 min, untimed or overnight) or resting/standing (≥ 10 min) in a step before the first heat step (`TimeEstimator.passiveLabel`). A marinade step that also mixes covers its unclaimed ingredients ("Marinate 1 lb ground beef with …"); otherwise the item names the first thing mentioned ("Marinate the chicken").
  - *Mix ahead:* a step before the first heat step that whisks/mixes/combines or puts things in a bowl/dish and names ≥ 2 ingredients takes its unclaimed ones; "Mix the sauce:" when the step (ingredient names masked) says sauce/slurry/marinade/dressing, "Put … in a small bowl" for the bowl form.
  - *Heat steps* are found with ingredient names masked ("cooking wine" doesn't count) and "stir fry sauce" / "ready to cook" excluded.
  - Items store ingredient IDs and render amounts from the scaled recipe; notes are shown cleaned ("(Note 3)" refs and alternative amounts like "6 oz," removed).
- **Model prep plan.** `@Generable GeneratedPrepPlan` (≤ 3 groups: chopAndPrep / mixAhead / getOut; items = short action without amounts + ingredient names, ≤ 8 each), temperature 0.2, 12 s timeout. *Decision:* the rules always own "Start early" (it comes from step times and passive classification); the model groups the rest. `PrepPlanner.map` validates: names map to recipe ingredients by name, catalog entry or name part, each once (a name listed twice in the recipe maps to the next unclaimed line); actions with digits or over 40 chars fall back to the group verb so amounts always scale; items covering nothing are dropped; > 25% unmatched names (inventions) or nothing mapped → nil → rules; uncovered ingredients go to "Get out". Prep details drop the cutting words when the model's action already says them.
- **Caching (decision).** Plans are computed when cook mode opens and cached in memory per recipe revision for the app's lifetime (`PrepPlanCache`, key = `PrepPlanner.fingerprint`: title, ingredient IDs/names/notes and steps, so any edit is a new key; scaled copies share it). The rules' plan shows instantly; with the model on, its plan replaces it only if nothing on the prep list has been ticked yet, so the list never shifts under the cook's finger. Not persisted: a SwiftData field would need a schema version for a cheap, recomputable value.
- **Repeated names after swaps.** `StepRewriter` now collapses repeats of the new name joined by "and", "&" or commas, each optionally with an article: "the ginger garlic paste and ginger garlic paste" → "the ginger garlic paste". On the Mongolian beef fixture with the swap applied and the original steps kept, step 5 still names the paste twice in separate sentences ("Add the ginger garlic paste, and fry for 30 seconds. Add the white parts of the scallions and the ginger garlic paste…"); that's what the targeted model rewrite is for.
- **Targeted step rewrites.** `StepRewrites.requests` (RecipeKit): an added ingredient no step mentions (the model picks the step), or a replace (not an amount change) whose new name appears ≥ 2× in a step it changed; at most 2 per proposal set, one per edit. The model returns `{stepNumber, text}` (`@Generable GeneratedStepRewrite`). `StepRewrites.validate`: one paragraph, changed, length ½× … 1.5× + 60 chars (≤ 600), every number token, duration (incl. word durations) and temperature (number + unit) kept, the new name present (whole word, plural ok), removed names absent after masking the new name and other ingredient names; "Step 3:" prefixes and quotes stripped. Any failure drops the rewrite. Each proposal records the edits it depends on (its own plus any other edit that changed that step).
  - *"I made this":* edits appear first; rewrites are fetched afterwards (a small "Checking whether any step needs rewording…" row) and appended as "Reword step N" toggles showing old (struck through) → new, **unticked by default** (decision: the user's recipe text shouldn't change unless they opt in). Unticking an edit unticks and disables its rewrites; save applies only rewrites whose dependencies are ticked, after the other edits.
  - *Ingredient check (import and re-check):* there is no proposal list there, so when the model is on and a chosen swap triggers a request, Save shows "Checking steps…", then a "Tidy up the steps?" sheet with the unticked rewrites and its own Save. No request, no model, or no valid rewrite → saves straight away as before.
  - Never for "Paste my version" (the user's own words) and never whole recipes. With the rules, no rewrite toggles appear; the collapse fix still applies.

### AlarmKit timers (change agreed with the owner; overrides the "On finish" part of Timers above)

- **Why.** On the owner's iPhone 15 Pro the old finish (system sound 1005, a single blip) and the `.default` notification sound were both silent with the silent switch on.
- **AlarmKit path.** Each started timer schedules an AlarmKit countdown (`AlarmManager.AlarmConfiguration.timer(duration:attributes:)`, a fresh alarm ID per schedule) with `AlarmAttributes<CookTimerMetadata>` (recipe title, step, timer title; tint = light `accent`). Countdown title = the timer's label ("Brown the beef"), alert title "<label>: done". It rings like the Clock app, through silent mode and Focus, and shows the countdown on the Lock Screen and Dynamic Island. Authorization (`requestAuthorization`) is asked the first time a timer starts, only when `notDetermined`; the route (alarms or notifications) is re-read on every start, so a change in Settings applies to the next timer. If scheduling throws (e.g. `maximumLimitReached`), that timer falls back to a notification. No pause button (the app's timers use a fixed end date) and no custom stop/secondary intents on the alert; the Live Activity has its own Stop button (see "Owner feedback, round 2").
- **Requirements found in the SDK** (`AlarmKit.swiftinterface`, Xcode 26.6): `NSAlarmKitUsageDescription` in `App/Info.plist` (the Info.plist is a checked-in file, not generated, so the key is there rather than in project.yml); no entitlement. The countdown's Lock Screen / Dynamic Island UI is a Live Activity drawn by a widget extension, so there's a new `MiseWidgets` target (`Widgets/`, bundle ID `$(BUNDLE_ID_BASE).widgets`, no entitlements) with an `ActivityConfiguration(for: AlarmAttributes<CookTimerMetadata>.self)`; AlarmKit starts and ends the activity itself. `NSSupportsLiveActivities` is set on the app as well. `CookTimerAlarm.swift` (metadata + tint) and `Theme.swift` are compiled into both targets; the widget has its own copy of the `Mise/` colour sets. `AlarmPresentation.Alert(title:)` without a stop button is iOS 26.1+, so 26.0 uses the (deprecated-in-26.1) `stopButton:` initialiser behind `#available`. `AlarmConfiguration` isn't Sendable, so it's built and scheduled in a `nonisolated` helper; only the Sendable attributes cross from the main actor.
- **Sync with the Lock Screen.** Cook mode observes `AlarmManager.alarmUpdates`. An alarm that enters `.alerting` finishes its timer in the app (banner + success haptic). An alarm that disappears was stopped or cancelled elsewhere: after its end time the timer stays as "Done" and the banner goes; before it, the timer is removed. Only alarm IDs already seen in an update count as disappeared, so a reschedule in flight isn't mistaken for a cancel. Cancelling in the app (chip, ✕, leaving cook mode) cancels the alarm; dismissing the banner stops an alerting alarm. The banner stays up (with "Stop") while something is sounding, otherwise it hides after 10 s as before.
- **Fallback (AlarmKit denied or failing).** The old local notification, plus `TimerTone`: a synthesised double beep (no bundled file) looped on an `AVAudioEngine` with the `.playback` session category, so it sounds on silent while Mise is in the foreground, until the banner is dismissed (2 min cap). It plays only for a fresh finish (< 30 s late), not for a timer that ran out while Mise was in the background.

### What can I cook? (post-v1 feature)

- **Entry point.** An ask card at the top of the Recipes tab (under the greeting): a multi-line `TextField` ("What can I cook? e.g. spicy, ground beef, under 30 min"), autocorrect off, return or the arrow submits (a vertical field turns return into a newline, so a newline is stripped and treated as submit), ✕ clears and brings back the full list, example chips when empty. Voice is the keyboard's dictation mic; no Speech framework. *Decision:* it **replaces** the old `.searchable` title search (two search boxes would be confusing); title words still work as keywords (whole word, or a prefix of 4+ letters). Not a separate tab: results open recipes on the same stack, so Back returns to them.
- **Parsing** (`CookQueryParser`, RecipeKit) works on words, so dictated run-ons parse like typed text. Order: "with what I have" phrases → time limits ("under 30 min", "half an hour", "an hour and a half", "forty five minutes", "in 20"; "more than an hour" is a minimum and ignored) and servings ("for 4", "for the two of us", "serves 6") → "quick/fast/weeknight" = 30 min unless negated ("no rush") → cues → catalog aliases (longest first: "ground beef" → `beef`) → cuisine words (the guesser's cuisine names, "Sichuan" → Chinese, "Asian" → four) → style words (spicy, light, comforting, noodles, soup, rice, stir-fry, curry; "nothing heavy" → light) → diet words ("vegetarian", "vegan", "no meat", "gluten free"). A negation cue ("no", "without", "don't want", "anything but", postfix "free") covers the items that follow, joined only by and/or/commas/the/any…, so "no pork or beef something spicy" avoids both and wants spicy. "Out of X" marks X missing; "sad / leftover / use up / before it goes bad" marks use-up. Bare "rice" is a style, not an ingredient. Anything left that isn't a stopword is a title keyword ("Mongolian", "pancakes").
- **Ranking** (`RecipeMatcher`, constants public). Hard filters: avoided ingredient (protein families: "chicken" covers chicken-thigh/breast; a word that is also a tag, "pork"/"beef"/"fish", covers everything tagged so, e.g. bacon), avoided tags, time limit, and "with what I have" (every missing item needs a known good/great swap). Time = the longer of stated and estimated (computed by the rules when not stored or stale). *(Superseded:* the finder used to count an overnight only when no time was stated; `TimeEstimator` now skips optional make-ahead overnights itself, so that workaround is gone — see "Stale and inflated time estimates".) Score: ingredient 10 (use-up 14), cuisine 8, style 6 each (an avoided style −6), title keyword 8 / ingredient-name keyword 4; pantry: −3 per missing item without a swap, −1 with one, +2 for "you have everything"; up to +2 for being well under the limit; liked +1, disliked −2, +0.2 per time cooked (max 5). If the question asks for anything, a result must match at least one of those things. Nothing passes → up to 3 close matches (fewest broken filters first) and the list of what was relaxed.
- **Pantry coverage.** Non-staples only. Missing = the pantry or the question says so, or specialty/rare and not "have"; common items are assumed (as in the ingredient check). A written alternative in the pantry covers it ("sherry or rice wine" with dry sherry). "You have everything" also needs every meat/fish/tofu to be in the pantry or named in the question. Swaps come from `SwapEngine`, good/great only, every component in the pantry or common and not missing.
- **Why line** (`CookWhy`, rules only): "Uses ground beef · spicy · ~30 min · missing Shaoxing wine — dry sherry works +2 more", "~40 min · you have everything", close matches "~40 min, over your 30 min" / "Has pork". The optional model-written why was **not** done (cost an extra call per search for little gain over the computed line).
- **Model path.** `RecipeAssistant.parseCookQuery(text:)` (default: rules). `FoundationModelsAssistant` (in its own file, `FoundationModelsAssistant+CookQuery.swift`) asks for `@Generable GeneratedCookQuery { ingredients, useUp, avoid, maxMinutes, cuisines, styles, servings, pantryOnly }`, temperature 0, 8 s timeout. `CookQueryMerge.merge` only adds to the rules' parse: ingredient/avoid terms must appear in the question or map to a catalog entry with an alias in it; a rules avoid beats a model want and a model avoid never removes a rules want; numbers must be written in the question and the rules' number wins; a cuisine must be named; styles are free (closed list, soft score); pantry-only needs a pantry-ish word. The UI shows the rules' results at once and re-ranks if the merged query differs ("Reading your question…" while it runs). Any error → the rules.
- **Tests.** `swift test`: 237 passed (28 new in `CookFinderTests`: a parameterised test of 22 phrasings incl. dictation run-ons plus 2 parsing tests, 18 ranking tests over the fixtures, 7 merge tests; existing tests unchanged). `xcodegen generate`; `xcodebuild build` for `generic/platform=iOS Simulator` (plus `build-for-testing`, which compiles the new UI test) and `generic/platform=iOS -allowProvisioningUpdates` succeeded. No simulator booted; `WhatCanICookUITests` was **not run**, and the model path hasn't met the real model.
- **Weak spots.** English phrase lists; "no pork and chicken" avoids both. Style detection is heuristic (a recipe with three vegetables and no cream/bacon counts as "light"). Proteins not in the pantry are assumed available (only "you have everything" is withheld). "hot" means spicy. Keywords don't fuzzy-match ("mongol" won't find Mongolian; "brocoli" is a keyword, not broccoli). No "cooked recently" signal (only `timesCooked` exists).

### Stale and inflated time estimates (a saved Mongolian beef showed "~2 hr 33 min")

The owner's saved beef (their 11-step version, stated 30) carried a model estimate of 635 min (153 active + 480 "chilling", overnight) computed from the original Woks of Life steps. Three fixes:
- **Stale estimates.** `TimeEstimate.basis` = FNV-1a hash of the steps, lowercased ingredient names and `TimeEstimator.rulesVersion` (now 2). Title, servings, quantities and cuisine don't affect it. A missing (all older data) or different basis = stale. `Recipe.refreshingStaleTimeEstimate()` replaces a stale estimate with the rules'; `currentTimeEstimate()` reads one without storing. *Central place:* `SavedRecipe.recipe`'s setter (every write of the current version: edits, Paste my version, I made this, adjust, reset, cook-mode swaps, cuisine) and `init`; `updateInsights` refreshes the original's estimate if its steps differ. `RecipeInsights.estimateTime` stamps whatever the assistant returns. *Decision:* this replaces "recompute only at import": a changed recipe now always gets the rules' estimate at once, and the detail screen asks the model to refine a rules estimate in the background (`EstimateRefresh.refine`, once per recipe version per launch, written only if the recipe is unchanged). A recipe with no estimate at all stays without one (Re-check still fills it).
- **Existing data.** `EstimateRefresh.sweep` runs once per launch (Recipes tab appearing) and refreshes stale estimates on current and original versions with the rules (not a revision, `updatedAt` untouched). So on the owner's phone the beef reads 35 min as soon as the updated app is opened; with Apple Intelligence on, opening the recipe then lets the model refine it within the bounds below. The finder ignores stale estimates too.
- **Model bounds.** `clamp(_:against:)`: the model's prep must be within [rules ÷ 2 (≥ 2), max(rules × 2, rules + 15)], untimed within [0, max(rules × 2, rules + 15)]. A part outside → the rules' value for that part (and a neutral reason, since the model's words may describe the rejected part); both outside → the rules' estimate. The old absolute clamp (60/120) is gone. The owner's beef with the proposal (60, 120): bounds prep 8–34, untimed 0–15 → rules, 35 min.
- **Optional overnights** (`TimeEstimator.isOptionalOvernight`): a clause starting "Or", "if making ahead", "make-ahead", "made … ahead / in advance", "a day ahead", "day before", "ahead of time", "in advance", "up to overnight", "if you have time", "if time allows" → the overnight is dropped and any stated wait in the clause kept ("30 minutes, or up to overnight" → 30). "Marinate overnight", "refrigerate overnight", "at least 4 hours or overnight" still count 8 h.
- **Waits during prep.** A parallel wait "while you prep/chop/prepare … the other ingredients" now adds the part longer than the prep (Woks of Life: 20 min marinade − 14 min prep = 6 min).
- **Fixture results (rules), before → after:** Woks of Life shortcut (stated 30): 505 min overnight → **30 min** (14 prep + 11 cooking incl. 8 untimed + 6 marinating; no "Realistically" line, since 30 isn't longer than 30). Owner's version (stated 30 on the phone, none in the fixture): 35 → **35 min** (17 prep + 16 cooking + 3 standing; with a stated 30 it's not a mismatch, so the detail shows "30 min" and no extra line; in the finder it counts as 35). Kung Pao 65, chow mein 30, curry 40, pancakes 40, pork belly 80: unchanged, so `InsightsUITests` figures still hold (not run). With gaps (60, 120) every fixture now stays at its rules figure (before: 195–665 min).
- **Tests:** `swift test` 262 passed (new: bounds, optional/required overnight, Woks of Life, genuine overnight, owner's stale estimate, basis, stamping). `xcodegen generate`; `xcodebuild build` for `generic/platform=iOS -allowProvisioningUpdates` succeeded. No simulator or UI tests run.
- **Weak spots.** Any rules change must bump `rulesVersion` or old estimates stay; bumping it also drops model refinements (rules at once, model again on next open). Optional waits other than overnight ("rest 30 mins if you have time") are still counted.

### Feedback about steps (time, heat and order changes, e.g. 5 minutes on high then 5 on low)

"I made this" used to turn step feedback into generic notes. *Supersedes* the M3 time rule ("needed 10 more minutes" → note) whenever a step can be found; with no step named it is still that note.
- **Rules first** (`StepFeedbackParser`, RecipeKit). Each clause is checked for step feedback before the ingredient rules: times (absolute, "instead of 30", "N more/less minutes", phases joined by "then", also across a comma or sentence: "…on high. Then 5 on low."), heat ("high flame", "on medium", "medium-high heat"), cover/uncovered, skipping ("skipped the toasting", "didn't marinate"), method (oven, air fryer, a °/degrees temperature) and order ("added X before/after/earlier/later/at the end"). "Skipped the cilantro" is still an ingredient removal.
- **Target.** Step number ("step 9", "the third step") wins; otherwise a score per step: label words ("Chicken:") 4, each mentioned ingredient 2 (+1 where it first appears; +2 more for order changes), a specific verb (toast, simmer…) 3 / "cook" 1, two or three shared nouns ("the vegetables"), and tie-breakers (has a time, a heat step, a heat phrase, a lid, the "instead of" number, the longest cook for a method change). The winner must be unique, score ≥ 3 and be *named* by the clause (a time alone never picks a step).
- **Rewrite** (`StepTextEditor`): only the sentence holding the step's main time changes (a time outside parentheses, the "instead of" one, the one naming the clause's ingredient); the label and other sentences stay verbatim. One phase replaces the time in the step's own style ("25–35 min" → "15 min", "1 hour" + 30 → "1 hour 30 minutes", ranges shift by a delta) and swaps or inserts the heat word; several phases are composed from the step's verb: "Cover and cook on low 25–35 min until tender (boneless: ~15–20 min)." → "Cook on high 5 min, then cover and cook on low 5 min until tender." (the lid goes with the phase at the step's old heat; parenthetical alternative times are dropped after an absolute change, kept after a delta). *Decision:* "until tender" is kept as the doneness cue.
- **Otherwise:** a skipped step becomes `.removeStep` (new `RecipeEdit` case, applied after every other edit, highest index first, so all indices refer to the saved steps) when no ingredient is mentioned only there and it isn't a partial skip ("didn't marinate" in a step that also mixes); method, order, partial skips and times the rules can't place become a note tied to the step ("Step 7 (Chicken): Did the chicken in the oven at 200°C").
- **Model.** `proposeEdits` sends the model only the feedback the step rules didn't use and always appends the rules' step edits. `proposeStepRewrites` also sends each step note marked for the model (≤ 2) with the step and its neighbours. `StepRewrites.validateFeedbackRewrite`: one paragraph, changed, ⅓×–2×+80 chars, every number/duration/temperature from the old step or the feedback, no old temperature dropped unless the feedback gives one, no catalog ingredient that neither names, label kept. A valid rewrite replaces the note (ticked). *Decision:* the rules' own rewrites are not sent to the model; it only handles what the rules could only note.
- **UI.** Step changes from feedback are ticked like the feedback's other edits (ingredient-tidy rewordings stay unticked); each shows "Was"/"Now" with ±5 words of context, the changed words struck through / highlighted, and "You said: …". Tapping the text opens a step editor (`StepEditSheet`); step notes get "Edit step N instead". Recipe detail: long-press a step → "Edit step" (revision "Edited step N").
- **Time estimate:** step edits change `TimeEstimate.basis`, so the existing refresh applies (tested: the owner's sentence makes the stored estimate stale and the refreshed one shorter).
- **Tests.** `swift test`: 287 passed (11 new tests, one parameterised over 21 phrasings across the pepper chicken, chow mein, kung pao, Mongolian beef, pork belly and curry fixtures; existing expectations unchanged). `xcodegen generate`; `xcodebuild build` for `generic/platform=iOS -allowProvisioningUpdates` succeeded. No simulator or UI tests run; the model path is only tested with hand-written outputs.
- **Weak spots.** English phrase lists. A step change computed from the saved step overwrites a swap's rename in the same step if both are ticked. "Them/it" isn't resolved ("cooked them 10 min longer" stays a note). Removing a step doesn't reword the next one ("Grind: Cool completely…" after skipping the toasting). A time inserted into an untimed step goes after the verb ("cook 5 min until…"). Several changes to one step in one go are chained only when each is a rules rewrite.

### Share a recipe with a friend (post-TestFlight feature)

- **Format** (`RecipeKit/Share/SharedRecipeFile.swift`): a `.mise` file, JSON, exported UTType `com.nishantroy.mise.recipe` (conforms to public.data + public.content, *not* public.json/text: a text type would let text-accepting apps and our own share extension's text path swallow it as "shared text"). Hard-coded, not derived from `BUNDLE_ID_BASE`, so files work between builds. Fields: `kind: "mise.recipe"`, `version: 1`, `recipe` (the sharer's current `Recipe`: notes, servings, cuisine, time estimate, source URL, web image URL; a local image URL is dropped), `sourceTitle` (the first-saved title when renamed), `sharedAt`, optional `photo` {base64 data, type}. Never: pantry, revisions, cook log, rating. `version` is bumped only for breaking changes; unknown keys are ignored, a higher version says "Update Mise". Limits: file ≤ 1 MB (checked before reading), photo ≤ 400 KB (bigger/unknown type: dropped, recipe still opens), title ≤ 300 chars, ≤ 300 ingredients / 200 steps / 100 notes, each text ≤ 5,000 chars, needs a title and ingredients or steps.
- **Size:** chicken-curry fixture (18 ingredients, 13 steps) 5.7 KB; small recipe 355 B; with the 12 MP stand-in cooking photo (145 KB HEIC stored) 197 KB. Upper bound with a 300 KB photo ≈ 410 KB.
- **Send:** recipe detail → share button in the toolbar, or ⋯ → Share recipe. With a photo (latest cooking photo, else a friend's shared one), a small sheet with "Include my photo" (on). The stored photo goes as is when ≤ 300 KB HEIC/JPEG, else it's downscaled to 1200 px and re-encoded. *Deviation:* `UIActivityViewController` with two `UIActivityItemSource`s (the "<Title>.mise" file in tmp, and the plain text) instead of `ShareLink` + one `Transferable`: a destination takes one representation of a Transferable, so Messages would get the file *or* the text. With two items, Messages and Mail send the text and the file; AirDrop and Save to Files only the file; Copy only the text. The temp file isn't deleted on completion (an AirDrop may still be reading); the next share clears the folder.
- **Receive:** Info.plist `CFBundleDocumentTypes` (Owner, `LSSupportsOpeningDocumentsInPlace` NO). `RootView.onOpenURL` (not the tabs, so a cold launch or one into onboarding keeps it) reads the file (`IncomingRecipeFiles.readOpened`: security scope, size first, our `Documents/Inbox` copy deleted), copies it into the App Group (`IncomingRecipes/<uuid>.mise`) and queues a `.recipeFile` entry in the existing share queue, so it survives the app being killed mid-sheet and waits behind other shared items. Without an App Group it's shown straight away. The sheet is `SharedRecipePreview`: photo, "Shared recipe" badge, title, servings/time/cuisine, "Originally from <host>", ingredients, steps, notes; Cancel / "Save recipe" → the usual ingredient check (pantry questions, swaps) → Save. Saved: a new `SavedRecipe` whose original is the friend's version (Reset to original returns to it), first revision "Shared with you" (+ ": swaps" if any), not counted as cooked.
- **Shared photo:** re-encoded on receipt by `CookPhotoProcessor` (≤ 1600 px, metadata stripped, thumbnail) and written as `Photos/shared-<recipe id>.heic`. No stored property (no schema V3): `SavedRecipe.displayPhotoURL(in:)` = latest cooking photo, else that file if it exists (one stat per card). `allPhotoNames` includes it, so deleting the recipe deletes it and "Keep only the latest photo" keeps it. Settings' photo count includes it.
- **Duplicates:** *Decision, kept simple:* same title (case-insensitive) or same source URL → a caution card "You already have …; saving adds this as a separate recipe". No Replace (it would throw away the existing recipe's cooking log and history).
- **Share extension:** activation rule changed from the dictionary to a predicate: web URLs (not file URLs), plain text, or `com.nishantroy.mise.recipe`. Checked on the Mac by evaluating the predicate against sample attachments (Safari URL, text, .mise: on; PDF, image, bare file URL: off). A `.mise` attachment is loaded (≤ 1 MB) and queued like an opened file, so the app shows the same preview.
- **Tests.** `swift test`: 319 passed (17 new in `SharedRecipeFileTests`: round trip, unknown fields, newer version, not-a-recipe and damaged inputs, size limits, photo dropping, file names, plain text). `MiseModelTests` (macOS, `xcodebuild test -scheme MiseModelTests -destination platform=macOS`): 26 passed (new `SharedRecipeTests`: the opened-file read used by `onOpenURL`, inbox clean-up, oversize refusal, queue entries, shared photo display/clean-up, real HEIC through the format and back, original = friend's version). `xcodegen generate`; `xcodebuild build` (`generic/platform=iOS -allowProvisioningUpdates`) and `build-for-testing` (`generic/platform=iOS Simulator`) succeeded. No simulator or UI tests run; the share sheet, document opening and AirDrop are untested until the phones.
- **Gaps.** The `.mise` icon is the generic document icon (no `UTTypeIconFiles`). If a `.mise` is shared from another app's share sheet, the row may show Mise twice (the app, as the file's owner, and the share extension); if that's confusing, drop the mise clause from the extension's rule (opening still works). A friend without Mise who gets it by AirDrop gets only the file. A received recipe without a time estimate or cuisine isn't re-enriched (the launch sweep and detail refresh fill the estimate). No "Replace" for duplicates. No UI test hook for opening a file.

### iCloud sync (SwiftData + CloudKit private database)

- **Capability.** App target only (`App/Mise.entitlements`): CloudKit container `iCloud.com.nishantroy.mise`, `aps-environment` (CloudKit's silent pushes), plus `UIBackgroundModes: remote-notification` in `App/Info.plist`. The share extension and widgets have no iCloud entitlement; the extension still writes to the App Group queue. **Automatic signing registered it:** `xcodebuild build -destination generic/platform=iOS -allowProvisioningUpdates` succeeded and the regenerated development profile lists `iCloud.com.nishantroy.mise` (development and production container environments) and `aps-environment`, so nothing had to be created in the developer portal by hand.
- **Store.** `Persistence.opened` opens `Mise.store` with `ModelConfiguration(cloudKitDatabase: .private("iCloud.com.nishantroy.mise"))`. Signed out of iCloud, SwiftData's CloudKit store still loads and works locally, and starts syncing (uploading what's there) once the device signs in. It only *fails to load* for a broken setup (missing entitlement, a model CloudKit rejects); then the same file is opened with `cloudKitDatabase: .none` instead of crashing, and Settings says "iCloud sync off — couldn't start". `MiseStore.container` defaults to `.none`, never `.automatic` (which would pick up the entitlement): tests and UI tests (`-uiTesting`, own store) never touch iCloud. SwiftData keeps persistent history on for both, so switching between them doesn't make the store read-only.
- **Schema V3** (`Schema.swift`, live models in `extension SchemaV3`, V2 frozen in `SchemaV2Models.swift`): every attribute defaulted or optional, no `.unique` (PantryEntry.key), no relationships; adds `CookPhoto` and `UserProfile.updatedAt`. V2 → V3 is a `.lightweight` stage (Core Data infers adding defaults, an attribute with a default and an entity, and dropping the constraint). A test builds the Core Data model from `SchemaV3.models` and checks CloudKit's rules (no constraints, defaults, external storage on `CookPhoto.data`). From now on only add optional/defaulted attributes and new models: CloudKit can't delete or rename fields once the schema is in production.
- **Duplicates** (`SyncDedupe`, run on every foreground and 2 s after a burst of `NSPersistentStoreRemoteChange` imports): pantry, one entry per key, newest `updatedAt` wins (`setPantry` also merges, `removePantry` removes all, `PantryView` and `snapshot` read `newestPerKey` so a duplicate never shows before the pass); profile, one row, prefs from the newest `updatedAt` (stamped by the `prefs` setter; a blank profile made on a new device before the synced one arrives is `distantPast` and loses), `onboardingDone` true if any is; recipes, one per `id` (only a restored backup shares IDs; newest `updatedAt` wins). A recipe created on two devices offline stays two recipes. Otherwise last writer wins per record (CloudKit's default).
- **Photos: `CookPhoto` model, not data on the recipe.** `name` (the same string the log entry already holds, "<uuid>.heic", or "shared-<recipe id>.heic"), `recipeID`, `createdAt`, `byteCount`, and `@Attribute(.externalStorage) data` (a CKAsset in CloudKit). Why a model: a photo on `SavedRecipe` would re-upload the recipe record's assets on every recipe edit and only fits one photo; log entries are JSON inside the recipe so they can't own a model; keying by name keeps the cooking log's JSON unchanged across V2 → V3. No relationship: CloudKit delivers records in any order, and nothing needs both ends present. Only the ≤ 300 KB photo syncs (same `CookPhotoProcessor` pipeline); **thumbnails are derived per device** and cached. Display and sharing still use file URLs: `CookPhotoStore` (now a store + a file cache in `Library/Caches/Photos`) writes the cached file from the store on first use (`ensureCached`, off the main thread in `LocalPhoto`); a photo that hasn't synced yet shows the placeholder and `LocalPhoto` retries on `CookPhotoStore.photosChanged` (posted after imports, sync dedupe and the file import). "Keep only the latest photo" deletes unreferenced photos only when older than an hour, since a photo can arrive before the log entry naming it. Settings' size now counts stored photos only (no thumbnails).
- **Moving the old files in.** On every launch (idempotent, a background task) `importLegacyFiles` reads `Application Support/Photos`, stores each photo not already stored (recipe found through the logs or the `shared-` name; orphans kept with no recipe), saves in batches of 20, and only after a batch's save succeeds moves those files into the cache; thumbnails without a photo go, and the folder goes once empty. A crash between the save and the move is handled (already-stored names are recognised and just moved). Unreadable files stay put.
- **Local-only, unchanged:** cook sessions (UserDefaults), the share queue and incoming `.mise` files (App Group), estimate-refresh state, the photo cache.
- **Settings → iCloud:** "iCloud sync on", "iCloud sync off — sign in to iCloud to sync" (`CKContainer.accountStatus` = no account), restricted / temporarily unavailable, or "couldn't start"; when on, "Last synced" and the last sync error from `NSPersistentCloudKitContainer.eventChangedNotification`. Refreshed on foreground and on `CKAccountChanged`. The Settings footer now mentions the user's own iCloud account.
- **Migration verified on the Mac** (`xcodebuild test -scheme MiseModelTests -destination platform=macOS`: 39 tests in 5 suites passed, 13 of them new). New fixture `MiseModelTests/Fixtures/V2Sample.store`, written by the 1.0 (2) model files unmodified (main at afba3f0, compiled into a throwaway SwiftPM tool under `.build-cache`; its `main.swift` is kept as `Fixtures/MakeV2Fixture.swift.txt`): two recipes (one with rating, 4 cooks, 2 revisions, notes, a 2-entry cooking log with a photo; one "Shared with you"), two pantry entries, a profile with non-default prefs. `v2StoreFromTestFlightOpensWithEverythingKept` opens it through `MiseStore.container` and checks every field, then writes V3 data and reopens; `v2PhotoFilesMoveIntoTheStore` runs the file import on it (log photo, shared photo, orphan, stray thumbnail; batches of 2; rerun; simulated crash before the move); `storeWrittenWithFrozenV2ModelsMigrates`; the V1 fixture tests now go V1 → V2 → V3 and still pass. `SyncDedupeTests` covers each merge rule. `xcodegen generate`; `xcodebuild build` (`generic/platform=iOS -allowProvisioningUpdates`) and `build-for-testing` (`generic/platform=iOS Simulator`) succeeded. RecipeKit is untouched (no `swift test`). Nothing ran against real iCloud: sync itself is untested until the phones.
- **Debug builds initialise the CloudKit development schema** (`CloudSync.initializeDevelopmentSchemaIfNeeded`, Apple's documented pattern: a throwaway `NSPersistentCloudKitContainer` with the SwiftData model on a scratch store, `initializeCloudKitSchema()`), once per schema version per install, before the store opens (a few seconds on that first launch; retried next launch if it fails, e.g. signed out). Release/TestFlight builds never do this.
- **Known gaps.** On a fresh install the onboarding screen shows until the synced profile arrives (it then switches to the tabs by itself); finishing onboarding first just makes those prefs the newest. Signing into a *different* iCloud account makes CloudKit remove the old account's synced data from the device (system behaviour). #### CloudKit environments and what the owner must do

- Builds run from Xcode (Debug, development-signed) use the CloudKit **development** environment. **TestFlight and App Store builds use the production environment**, which starts with no schema: until the schema is deployed, a TestFlight build's sync fails (records can't be saved; the app still works locally).
- **Before uploading the TestFlight build with sync:**
  1. Build and run the **Debug** build from Xcode on an iPhone signed in to iCloud (the owner's own). On first launch it pushes the schema to development (Console, subsystem "Mise", category "Sync": "CloudKit development schema initialized"). Also save a recipe, a pantry item, onboarding prefs and a cooking photo, to be safe.
  2. Open CloudKit Console: https://icloud.developer.apple.com → sign in with the developer account → CloudKit Database → container **iCloud.com.nishantroy.mise** → environment **Development**.
  3. Schema → Record Types: check `CD_SavedRecipe`, `CD_PantryEntry`, `CD_UserProfile` and `CD_CookPhoto` exist (CookPhoto with `CD_data_ckAsset`).
  4. Optional, for debugging: Schema → Indexes → each record type → add a **Queryable** index on `recordName`, so Records → Query can list them in the Console (sync itself uses zone changes and doesn't need it).
  5. Click **Deploy Schema Changes…** (bottom left in the Development environment), review, **Deploy**. Production now has the same record types.
  6. Then archive and upload as usual. Repeat steps 1–5 whenever a future schema version adds attributes or models, *before* uploading that build.
